# 运营顾问字段冻结与升级机制

文档版本：1.1\
更新日期：2026-09-11\
适用范围：运营顾问 Workflow 首次诊断、Chatflow 多轮追问，以及调用它们的前后端。\
面向人员：产品负责人、前后端开发、Workflow 维护者和参与修改的 AI 助手。

**当前状态：维护流程已写明，字段仍为候选，尚未正式冻结。自动差异检查和发布拦截尚未实现。** 本文档的版本号不代表接口已冻结，也不修改现有报告中的 `schema_version="1.0"`。

## 1. 这套机制解决什么问题

后端按照一套固定字段开发后，后续优化 Workflow 必须继续返回这套字段。即使换了模型、提示词或知识库，开发也应当能够继续调用原接口。

确实需要改字段时，先明确哪些调用方会受影响，再按新契约升级。AI 可以提出新字段和修改方案，但不能在“优化效果”的过程中直接替换已经冻结的字段，也不能顺手修改旧基线，让检查结果看起来通过。

日常维护按下面的顺序进行：

```text
第一次：盘点候选字段 → 解决冲突 → 产品与开发确认 → 保存冻结基线

以后：读取冻结基线 → 判断是否改接口 → 测试应用验证
                                  ↓
                 接口不变：更新实现版本
                 接口有变：确认新契约、迁移与回退方案
                                  ↓
                        检查通过 → 发布并留档
```

## 2. 三份文件分别管什么

| 文件 | 回答的问题 | 维护方式 |
|---|---|---|
| 本文《运营顾问字段冻结与升级机制》 | 以后怎么改、谁确认、怎么发布和回退 | 流程有变化时更新，保留文档修订记录 |
| [运营顾问 Workflow / Chatflow 字段说明](运营顾问Workflow字段说明.md) | 当前有哪些字段、分别是什么意思 | 作为字段字典随契约维护，冻结时保存准确快照；不自行新增接口事实 |
| [V1 单 HTML 字段对照](运营顾问-v1字段说明.html) | 哪个字段对应哪个界面、哪个交互 | 跟随字段说明和原稿同步，注明示例与未接入范围 |

项目根目录的 [AGENTS.md](../../AGENTS.md) 负责要求 AI 遵守本机制；[CONTEXT.md](../../CONTEXT.md) 负责记录当前使用哪个版本、哪些工作已完成、哪些仍待办。

正式冻结后，以**已确认、按版本保存的机器可读契约及确认记录**为对照标准。说明文档和 HTML 是配套阅读材料。发现契约、代码、DSL 或文档不一致时，先记录差异并查明原因，不能默认把最新生成的文件当成新标准。

### 字段文档本身也是必须维护的交付物

字段字典与机器可读契约共同纳入版本包。机器定义约束可检查的结构，字段文档解释业务语义、来源、单位与页面用途；缺少任何一方，都不能宣布本次字段交付完整。

冻结范围内，每个字段都应能查到：完整路径与所属接口、类型、是否必填、默认/空值规则、业务含义和单位、枚举与容量、生产方和消费方、示例、状态及适用版本。内部参数要与对外字段分开，尚未定义的项要保留待办，不能用猜测补成正式约定。

一次升级应同时核对字段字典、Schema、DSL、后端、UI 映射和固定样例。需要变化的材料随候选版更新，不受影响的材料记录核对结论。验收时检查新增、删除、改名和规则变动是否逐项出现在字段文档中；只改运行逻辑而漏改字段说明，不算交付完成。

冻结时保存字段文档的版本、准确快照和对应契约关系；旧版文档保留，不能用新版覆盖旧版后还声称旧版可追溯。机制文档只在维护流程变化时更新；不能用更新机制文档代替更新具体字段定义。

## 3. 要冻结的是整条调用链

冻结的内容不只是变量名字，还包括类型、是否必填、允许为空的方式、业务含义、单位、枚举、长度与数量上限。

| 层次 | 应记录并冻结的范围 |
|---|---|
| 页面 → 后端 | 请求字段、来源标识、长度限制、报告和会话的关联规则 |
| 后端 → Workflow | `module`、`function_name`、`report_id`、`business_context`；请求层参数与 `inputs` 分开记录 |
| 功能路由 | 8 个板块、32 个规范功能名称及已有别名；功能显示文案和路由标识不能随意混改 |
| Workflow 原始出口 | 正常、`repaired_`、`invalid_`、`failed_` 四个互斥分支的字段名、类型和状态含义 |
| 归一化报告 | 11 个业务字段、4 个身份字段及全部子字段；成功与失败结构分开记录 |
| 页面展示 | 28 份报告模板的表头、列顺序、摘要容量、消费位置；四个看板入口的未接诊断状态 |
| Workflow → Chatflow | `module`、`business_context`、`diagnosis_context`，报告封装及容量限制 |
| Chatflow 请求与回复 | `query`、`conversation_id`、后端结果字段；新报告开始新会话的规则 |

例如，`report.rows` 在 Dify 原始出口是字符串还是二维数组，与页面最终拿到的二维数组，是两个不同边界，必须分别写清。不能只写“前端最后能显示”，就认为上游字段已经统一。

目前 `business_context` 是自由文本。可以明确冻结它的外层类型和容量，但不能因此声称商品、周期、指标等内部业务字段也已经固定。后端需要按固定键名传资料时，必须先定义并确认该部分契约。

## 4. 第一次怎么冻结

| 步骤 | 要做什么 | 完成标志 |
|---|---|---|
| 1. 确认范围 | 确定本次交付包含哪些功能、数据来源、输入和输出；未接入功能明确列出 | 有范围清单，不把注册入口等同于可用功能 |
| 2. 对齐候选 | 对照最新 Workflow/Chatflow 导出、后端校验、字段文档和原稿，列出冲突 | 每个冲突有处理决定，或被明确排除在本版承诺之外 |
| 3. 准备契约 | 固定字段定义、约束、各分支及样例；未定义的内容不能被标为已冻结 | 有完整、可校验的版本包 |
| 4. 验证候选 | 运行离线检查，在测试应用完成适当的真实调用，并核对页面 | 记录测试范围、结果及限制，没有阻断本次范围的问题 |
| 5. 确认冻结 | 产品确认业务含义与界面；前后端开发确认调用和消费方式；维护者确认 DSL 一致 | 有确认人、日期、版本和确认范围；AI 不能代替相关方确认 |
| 6. 保存基线 | 保存准确的文件快照、哈希、Git 版本和验证结果，再标记为 frozen | 下一次修改能找到并复现同一份基线 |

冻结记录需要指向准确的文件版本。只写“V1 已确认”，但没有说明确认的是哪份文件，不算完整记录。

### 冻结版本包的内容

建议在首次确认时使用 `contracts/operations-advisor/1.0/` 作为基线目录。**该目录目前尚未创建，以下是未来冻结时的归档要求。**

| 归档内容 | 用途 |
|---|---|
| 契约清单、字段字典准确快照和机器可读定义 | 覆盖各层输入、输出、路由、表头及约束，明确本次冻结范围和对应文档版本 |
| 对应的 Workflow / Chatflow DSL | 还原被验证的节点、提示词、模型配置和分支；敏感值须脱敏 |
| 固定输入与预期结果样例 | 覆盖成功、资料不足、修复成功、输入错误、生成失败等路径，使用虚构资料 |
| 冻结确认记录 | 记录产品及开发确认、文件清单、哈希、Git commit 和验证证据位置 |
| 发布记录和回退记录 | 标明测试/生产应用、对应实现版本、切换范围及旧版保留位置 |

冻结基线按版本保留，不原地覆盖。后续实现可以引用它；需要变更契约时，建立新版本并重新记录差异。旧基线的勘误也必须留痕，不能静默修改。

DSL 中若含凭据，只归档脱敏副本并记录脱敏范围；公开版本包不得包含 Key、Token、Cookie 或真实客户资料。验证与归档应能追溯到同一次发布。

## 5. 以后修改时，先判断改的是哪一种

| 修改内容 | 处理方式 |
|---|---|
| 换模型、调整提示词、优化知识检索、修复内部代码；外部字段与承诺均不变 | 保持契约版本，增加实现版本，完成回归后发布 |
| 调整中文说明文档中的措辞，业务含义和限制不变 | 修改文档并留修订记录，不改变接口 |
| 新增、删除、重命名字段，改变类型或必填性 | 按契约变更处理；先列差异，再确认新版本与迁移 |
| 改枚举、单位、表头、列顺序、长度/数量限制或错误含义 | 同样按契约变更处理，不能归为普通提示词优化 |
| 只想修改功能显示名称 | 先核对路由；当前 `function_name` 也承担路由作用，不能直接改名 |

**新增“可选字段”也不自动等于兼容。** 当前报告 Schema 使用 `additionalProperties: false`，后端会拒绝多余字段。是否兼容必须检查实际调用方，不能凭字段看起来无害就直接发布。

版本分开管理：

- **契约版本**：表示对外字段与行为约定。现有报告值为 `schema_version="1.0"`，本次写文档不会改它。
- **实现版本**：记录哪次 Workflow、提示词、模型或代码修改，例如 `r001`、`r002`。这是维护记录示例，不是新增 API 字段。
- **文档版本**：表示本文流程说明的修订，与前两者分开。

例如，契约保持 1.0，提示词优化后实现从 r001 到 r002。若将 `report.points` 改成另一字段或改变结构，则提出契约 2.0，并安排调用方迁移；这些版本号是示例，不能据此宣称已有冻结版本。新版本还需要后端识别、校验和路由支持，不能只改报告里的版本字符串。

## 6. 一次升级怎么走完

1. **读取基线。** AI 和维护者先读本机制、CONTEXT 中的当前版本、冻结契约及相关代码，不从上一次对话重建字段。当前尚未冻结时，先使用字段说明及现有机器定义作候选依据。
2. **列出差异。** 说明修改目的；逐项列出字段路径、旧值/旧规则、新值/新规则、受影响页面、前后端和 Chatflow。不改接口也要记录“契约无变化”。
3. **准备可审查结果。** 准备候选 DSL、样例、兼容性判断、验证结果及迁移/回退方案。需要批准的契约变化应形成具体材料后再交用户和开发确认；会话中已经明确批准的内容不重复询问。
4. **在测试应用验证。** 使用测试应用或受控候选版本，不先覆盖生产应用。固定字段基线不能随实现一起改写来消除失败；新契约的基线变更单独审查。
5. **按依赖顺序切换。** 接口不变时更新实现；不兼容升级先让后端、前端及 Chatflow 支持新版，再切换调用范围。确认有明确的版本路由或隔离方式，不能假设两个版本会自动兼容。
6. **发布并留档。** 记录应用和发布版本、代码版本、测试结果、确认记录、切换时间与回退目标。完成发布后，用约定的样例核验实际结果。

旧报告和进行中的追问会话，继续按其原契约处理；新报告按新版本建立会话。迁移期间不得将新版报告直接塞进不支持它的旧会话。旧版停用条件应提前约定，包括是否仍有旧调用方、报告或会话依赖。

## 7. 发布前检查什么

| 检查项 | 判断标准 |
|---|---|
| 字段、字段字典与 Schema | 输入、输出、嵌套字段、必填、枚举、容量与冻结版本一致；或属于已确认的新契约差异；文档中的语义、示例和消费位置同步，不能遗漏字段变更 |
| 全部分支 | 正常、修复、输入错误、生成失败均符合约定；Dify 运行成功与业务 `status=ok` 分开检查 |
| 归一化与身份 | `rows` 能按约定还原；报告 ID、功能、板块与追问上下文一致；错误报告不能作为成功结果交给页面 |
| 功能与 UI | 按声明支持的功能逐项核对路由、原稿表头、摘要上限；未接入范围没有被包装成已可用 |
| Chatflow | 当前报告正确交接；同报告续问沿用会话；新报告不会串入旧会话 |
| 旧调用方兼容 | 用旧版请求和消费代码验证新版；不兼容更新核对迁移顺序及旧版保留方式 |
| 发布与回退材料 | 能准确找到候选版、上一可用版、对应代码和应用配置引用；无明文凭据 |

本项目当前已有以下测试文件，可作为检查的一部分：

```bash
node --test tests/operations-workflow.test.js tests/operations-chat.test.js
npm test
```

上述命令在项目根目录运行。它们是现有代码测试，**不是已实现的 DSL 冻结差异检查器**，也不代替真实测试应用调用。固定样例应覆盖契约规则，不只断言某一段模型文字；真实调用另外检查业务内容和界面效果。未完成的验证必须注明，不能以静态检查通过代替线上验收。

未来自动检查器应读取只读的已确认基线，对比新 DSL、契约、后端和页面定义，输出差异并在未获确认时返回失败。随后才能接入受保护的发布流程。只写一个本地脚本，无法阻止人在 Dify 中绕过流程直接编辑生产应用；要形成技术拦截，还需团队约束发布权限和发布入口。

## 8. 出问题如何回退

发现结构校验失败、旧请求不兼容、报告与会话错配，或核心页面无法消费结果时，停止扩大新版使用范围。按发布记录把调用切回上一套已验证的应用实现、契约适配和代码版本，并用固定样例复核。

回退必须按兼容组合进行，不能只还原提示词而保留不兼容的后端。旧报告和会话仍按原版本处理；无法安全恢复的任务明确报错并重新生成，不能默默替换成静态成功内容。如果以后增加不可逆的数据迁移，要在升级前另外准备恢复方案。

回退后记录触发原因、受影响范围、恢复目标及复核结果；修复后的版本重新走测试和发布流程。

## 9. 维护记录模板

以下内容写入对应版本包的记录中，方括号内容由本次负责人填写，不能用示例冒充实际确认。

```text
变更目的：[为什么修改]
当前基线：[契约版本、准确文件位置和哈希；未冻结则明确填写候选]
目标版本：[契约版本 / 实现版本]
变更分类：[契约无变化 / 契约有变化]
字段差异：[路径、原规则、新规则、影响；无变化则写明]
本次支持范围：[功能、数据来源、页面、调用方]
兼容与迁移：[旧请求、旧报告、旧会话如何处理，切换顺序]
验证记录：[样例、离线检查、真实调用范围、结果与证据位置]
冻结或升级确认：[产品、前后端开发、维护者及日期；未确认不得填已冻结]
发布记录：[测试/生产应用引用、DSL 与 Git 版本、切换范围和时间]
回退目标：[上一可用组合、保留位置、复核方法]
当前状态：[候选 / 已冻结 / 测试通过 / 已发布 / 已回退 / 已退役]
```

这些是维护记录，不是要求在 Workflow 的开始节点中增加一组输入字段。冻结、验证和发布是不同事实，应各有记录，不能因为“已冻结”就同时填“已发布”。

下次交给 AI 维护时，可以直接使用：

> 请先阅读 AGENTS.md、《运营顾问字段冻结与升级机制》和 CONTEXT.md 指向的当前契约。先列字段差异，再修改实现；对外字段不变时保持契约版本。不得覆盖冻结基线或修改旧断言来掩盖差异。交付时给出候选文件、检查结果和回退目标。尚未冻结的内容必须明确标为候选。
